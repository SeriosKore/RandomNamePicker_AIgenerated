# 插件体系改进建议（评审：插件开发文档 × 宿主代码）

> 评审对象：《插件开发文档.md》（V1.1.0，671 行）+ 宿主源码 `src/com/randomnamepicker/plugin/**`、`mode/**`、`ui/**`、`floating/**`、`core/**`、`main/**`、`theme/**` + `examples/` 全部示例工程。
> 评审方式：**只读交叉比对**（文档声明 ↔ 宿主实现 ↔ 示例插件），未修改任何源码、文档与产物。
> 评审问题：① 现行文档与宿主是否满足**别的开发者**开发插件的需求？② 是否需要更多宿主改动？③ 若要改，怎么改？
> 结论先行：**基本满足“宿主受控协作者”开发模式/按钮类插件；但要支撑“陌生第三方独立开发、调试、分发插件”，宿主侧还有若干结构性缺口，值得改动。** 本文按 P0（强烈建议）/P1（建议）/P2（可选）给出 13 条改进建议与 1 份纯文档修订清单；每条含现状证据、对第三方的影响、宿主改动方向与成本提示。**未写一行生产代码，方案均为设计草案。**

---

## 0. 评审结论速览

| 维度 | 评价 |
|---|---|
| 文档质量 | **优秀**：机制说明、API 参考、线程模型、红线、验收清单、QA 样例对照齐备，远高于一般内部项目文档 |
| 宿主加载机制 | **扎实**：整 jar 原子事务、暂存-提交、冲突预检、防御执行、EDT 规约设计正确，示例与坏样例验证充分 |
| 满足“加一个模式/加几个按钮” | **满足**：`registerModeHandler` + `addUiAction(UiZone,…)` 覆盖典型诉求，正计时子球插件证明“宿主零改动”可做较深集成 |
| 满足“第三方开发者”的充分性 | **有缺口**（本文核心）：①公开/内部 API 边界无权威定义与强制；②无插件与宿主间的版本契约；③拒载/状态只进日志、UI 无感知；④插件无法订阅宿主事件（抽取结果/方案/模式/锁变化），只能 AWT 全局监听+轮询绕路；⑤`ModeHandler` 契约表达力有天花板；⑥加载顺序/分组/图标/自持数据等生态性能力弱；⑦无测试与诊断工具链；⑧信任/安全模型未如实文档化 |
| 是否需要更多宿主改动 | **是**（若以“向第三方开放”为目标）。不需要改动的最小集见 §6“只做三件事” |

三条最值得先做的宿主改动（P0 前三，详见 §4）：

1. **定义并固化“插件公开 API 面”，把‘仅文档约束’升级为‘宿主可校验’**（打包禁令、内部类可达性、密码/锁可达性）。
2. **为宿主状态提供结构化事件与查询**：抽取开始/结束（含结果）、方案切换、模式切换、锁状态、插件集变化——消灭“AWT 全局监听 + 轮询”这类绕路写法。
3. **加载结果与运行状态可观测**：拒载原因、成功清单、运行期异常能通过宿主 UI 与只读 API 呈现，而不是只落在 `Modifylog.txt`。

## 2. 现状优点（为什么说“基本满足”）

评审先给结论性肯定，避免后续改进建议被误读为全盘否定：

1. **文档与实现一致性高**：`PluginContext` 的注册/服务面、`UiZone` 9 个区域、冲突预检、拒载语义等文档描述与代码逐条对得上（差异点已列入 §5 文档修订清单）。
2. **加载模型严谨**：`PluginManager.loadOneJar`（`PluginManager.java:339-399`）实现“遍历全部 .class → 实例化 → onLoad → 冲突预检 → 整体提交”，任一步失败整 jar 拒载回滚（`rollbackLoaded`、`closeQuietly`），不污染 UI 与其它 jar。
3. **防御执行到位**：`canPick/nextCandidate`、模式附加按钮、菜单/按钮回调均有 try/catch（`NamePickerApp.java:475-497`、`PluginManager.java:591`）。
4. **线程模型与文档规约一致**：`onLoad` 在 `plugin-loader` 后台线程（`PluginManager.java:246`），提交成功后在 EDT 一次性刷新（`:329-331`、`:501-513`）；示例（正计时子球）遵守“onLoad 只注册 + `invokeLater`”。
5. **有真实的高水位案例**：`examples/plugin-timer` 证明在不改宿主前提下能做到自绘子窗、AWT 观察、自持配置——这反过来也暴露了缺宿主钩子时第三方的绕路成本（见 R4）。
6. **刻意取舍都有记录**：热插拔、UI 选项面板、签名/权限、插件间依赖解析等在交付报告中已列“明确不做/后续”（`documents/Stage3_交付报告.md:80`、`documents/插件UI槽二期交付报告.md` §6）。

因此结论是：**对“宿主作者本人/受控协作者按文档自约束开发”，现行体系够用；对“陌生第三方”，缺的是生态性、可诊断性、契约性与信任边界，而不是加载内核。**

### P0-1 定义并固化“插件公开 API 面”，把文档约束升级为宿主可校验

**证据**
- 文档称“宿主不暴露：`PasswordManager`、`ConfigManager`、`FloatingBall`、`NamePickerApp`……插件拿不到这些类型”（`插件开发文档.md:84`、`PluginContext.java:22-26`），且红线“依赖宿主内部类/私有字段 = 破坏版本兼容承诺”（`插件开发文档.md:616`）。
- 但事实上**所有宿主类都是 public 且经 parent-first 类加载器可达**（`PluginManager.java:343-344` 以宿主类加载器为 parent）。所谓“不暴露”只是 `PluginContext` 不提供句柄，**类本身在编译期可见、运行期可反射**。例证：
  - 官方推荐范本 `examples/plugin-timer/FloatingBallTracker.java:2` **直接 `import com.randomnamepicker.floating.FloatingBall`**（宿主窗口类），并靠 `instanceof FloatingBall` 探测宿主悬浮球（`FloatingBallTracker.java:248-256, 375-381`）——与文档“不 import 任何宿主窗口内部类”（`插件开发文档.md:557`）自相矛盾。
  - `PasswordManager.unlock()`、`PasswordManager.lock()` 是 **public static**（`PasswordManager.java:158-164`），`ConfigManager.properties` 是 **public static** 字段（`ConfigManager.java:8`），`ModeRegistry.register/unregister` 是 public static（`ModeRegistry.java:71-94`）。一个越界插件完全可以在 `onLoad` 里 `unlock()` 绕过锁定、`ModeRegistry.unregister("name_list")` 删掉内置模式、或直接 `ModeRegistry.register(...)` **绕过暂存-提交与冲突预检**污染内置下拉数据源——这些都没有任何宿主侧拦截。
- 交付报告自己也写明这是“受控 API + 可信插件，仅文档约束禁打包 API 类”（`documents/Stage3_交付报告.md:80`）。

**第三方影响**
- 第三方无法从代码/工具上分辨“哪些是受支持的 API”，只能靠人工遵守文档；越界用法（反射、import 内部类）不会报错，但宿主一升级即碎，责任却落到插件作者头上。
- 恶意/失误插件可直接触碰密码与锁状态、改写宿主配置与内置模式，破坏宿主自身保证（“内置模式不可移除”“插件不能绕过锁修改名单/方案”）。

**宿主改动方向（选一或组合，成本递增）**
1. **权威白名单 + 文档化“公开面”**：在 `plugin` 包内发布一页“受支持公开 API = plugin/mode/core(model 只读)/`ModeHost`/UiZone 之方法清单”的常量或独立 javadoc 页，并把 `PasswordManager/ConfigManager/DataManager 构造器/ui/floating/theme` 明确标注为“宿主内部、不承诺兼容”。成本：低，纯文档+注释。
2. **轻量加载期自检（推荐）**：`PluginManager` 扫描 jar 时，对 jar 内出现 `com/randomnamepicker/**` 条目**记警告或直接拒载**（现状只是文档约束；`collectClassNames` 处已遍历全部条目，加一个前缀检查即可）。对插件字节码引用宿主内部类做完整校验成本高，可先不做；至少对“jar 内打包了 API/宿主类”这种必错情况给出确定性结果。
3. **收紧静态旁路**：把 `ModeRegistry.register/unregister` 改为非 public（或由 `PluginManager` 独占调用）、把 `PasswordManager`/`ConfigManager.properties` 对插件不可见——但后者需要模块化或 SecurityManager，成本高，见 §7“不建议”。
4. **信任模型如实文档化**：见 D1。

**成本/兼容性**：1、2 低且零破坏；3 需小范围改 `mode/plugin` 两个包并回归内置模式；4 纯文档。

### P0-2 宿主状态事件化：抽取结果/方案/模式/锁/插件集变化可订阅

**证据**
- `ModeHost` 只提供 6 个只读 getter（`ModeHost.java:23-47`），没有任何订阅/事件入口；`PluginContext` 同样没有。
- 唯一的“监听”是 `PluginManager.addUIListener(Runnable)`（`PluginManager.java:268`），注释与用法都表明它是**宿主内部**用于 EDT 刷新（`NamePickerApp.java:64`、`Main.java:36`），不是给插件的事件总线。
- 抽取结果目前只以字符串写日志：`logResult()` 取 `displayLabel.getText()` 拼“方案-模式=结果”（`NamePickerApp.java:514-521`）。插件拿不到结构化结果（方案、模式、值、时间）。
- 悬浮球针对“当前模式”的右键项是对**内置模式显示名硬编码 switch**（`FloatingBall.java:120-141`：“名字列表模式/数字模式/座位模式”）；插件模式在该菜单里永远没有“模式专属配置项”，只能注册全局项。
- 高水位案例正计时子球为感知“悬浮球几何/单击/双击”，用**全局 AWTEventListener（`Toolkit.addAWTEventListener`，`FloatingBallTracker.java:71-100`）+ `Window.getWindows()` instanceof 轮询**（`FloatingBallTracker.java:248-256`），并在方案里明说这是“宿主无官方槽时的路线”（`documents/正计时子球开发方案.md`）。二期交付报告的“后续展望”也点名“自绘 UI + 窗口级交互（生命周期/几何订阅钩子）”（`documents/插件UI槽二期交付报告.md` §6）。

**第三方影响**
- 想做“抽取历史/统计/结果音效/结果导出/自动联动”的第三方插件没有任何官方钩子，只能解析日志文本或轮询 UI——脆弱且不可靠。
- 想做窗口级交互（跟悬浮球、跟主窗状态）只能 import 内部类 + AWT 全局监听（见 P0-1 的灰色地带）。
- 插件模式无法表达“我当前被选中了/被取消”或“我的一次抽取结束”，状态管理只能自造。

**宿主改动方向（设计草案，建议新增而非改动既有方法）**
1. **抽取生命周期事件**（最有价值）：在 `logResult()` / `stopPicking()` / `startPicking()` 的成功与失败出口发事件，载荷含（方案名、模式 modeId/displayName、结果字符串、时间、是否由悬浮球触发）。事件在 EDT 派发，每个插件回调 try/catch。
2. **宿主状态事件**：方案切换（`onSchemeChanged`）、模式切换（`onModeChanged`）、锁状态变化、插件集变化（沿用现有 `addUIListener` 时机即可）。
3. **给插件的注册入口**：`PluginContext` 增加形如 `void subscribe(HostEvent.Type type, EventListener l)` / `unsubscribe(...)`（实现类为 `PerPluginContext`，`onUnload`/拒载回滚时宿主自动清理，杜绝插件忘退订导致悬空引用——这对第三方尤其重要）。
4. **窗口级能力（可选，P1）**：宿主提供“悬浮球/主窗几何只读快照订阅”或至少官方 `isFloatingBallVisible()`/位置查询，替代 `FloatingBallTracker` 的轮询；并为“当前模式右键菜单”开放一个模式可参与的口子（把 `FloatingBall.java:120-141` 的硬编码 switch 换成“模式可选提供右键配置项”的注册，保持内置行为不变）。
5. 事件负载用不可变 DTO（只含值对象/字符串），避免把宿主 UI 对象传给插件而固化内部依赖。

**成本/兼容性**：事件总线是增量，风险低；建议最先做 1+3。几何订阅（4）涉及 `FloatingBall` 结构，放 P1。

### P0-3 加载结果与运行状态可观测（宿主内置“插件状态”视图 + 只读查询）

**证据**
- 加载成功逐插件记 `PLUGIN_LOADED`，拒载记 `PLUGIN_LOAD_ERROR` 且**只进 `log/Modifylog.txt`**（`PluginManager.java:382-397`）。
- 主窗“插件”菜单只显示动作项 + 只读“名称 版本”项（`NamePickerApp.java:373-395`），**不显示哪些 jar 被拒、为何被拒**；`getPluginInfos()` 也只含成功者（`PluginManager.java:528-535`）。
- 文档第 11 章也承认排查要“看 `log/Modifylog.txt`”（`插件开发文档.md:575-586`）。

**第三方影响**
- 终端用户装了第三方插件没生效，界面毫无提示，只能让用户翻日志文件——第三方分发时最常收到的反馈就是“装了没反应”。
- 第三方在开发期要反复重启看日志，无法获得“本 jar 是否被拒、冲突对象是谁”的结构化原因。

**宿主改动方向**
1. `PluginManager` 为每个 jar 保留 `LoadOutcome {jar, status(LOADED/REJECTED), pluginNames, reason, timestamp}` 的只读快照（内存即可，无需落盘），并暴露查询：`List<LoadOutcome> getLoadHistory()`、按 jar 查询。
2. 在设置窗（或主窗“插件”菜单）增加只读“插件”状态入口：列出 成功清单 / 拒载清单（含原因与建议）；拒载时给一行可读文案（如“模式 displayName 与内置冲突”“onLoad 抛异常：…截断”）。实现可复用 `PluginUiSupport` 的 Zone 思路新增一个宿主面板，不涉及插件 API 改动。
3. 若做 P0-2 的事件总线，插件集变化事件里携带 outcome 摘要。

**成本/兼容性**：纯增量、零破坏。查询与 UI 建议在 P0-2 之后或并行。

### P0-4 插件/宿主版本契约与 API 演进策略

**证据**
- 插件无法声明“需要宿主 V≥X/Y”；宿主也无法在加载时给出“该插件面向的宿主 API 版本不符”的明确诊断。现在插件编译时以宿主 jar/out 为类路径（`插件开发文档.md:254-266`），运行期任何 API 变化都表现为 `NoSuchMethodError/NoClassDefFoundError/链接错误`，被笼统记为“类条目加载失败”（`PluginManager.java:350-353`）。
- 文档仅提示 class 版本 ≤ 宿主 JRE（`插件开发文档.md:266`），对“宿主 API 版本”只字未提。
- 交付报告明说“宿主源码若后续再变，先重编宿主再编插件”（`documents/正计时子球开发方案.md:250`）——这是受控协作者流程，不是第三方分发模型。

**第三方影响**：无法表达兼容矩阵；宿主一升级，已分发插件可能静默失效且原因难查。

**宿主改动方向**
1. **宿主暴露常量 API 版本**：如 `PluginContext.getHostVersion()`（返回形如 `"1.1.0"` 或整数 API level），加载期由插件可选声明。
2. **插件元数据最小契约**：优先走 jar `MANIFEST.MF` 属性（如 `Plugin-Name/Plugin-Version/Host-Version-Min`），`PluginManager` 读取并校验、不匹配时给出明确拒载原因——避免为 `Plugin` 接口加抽象方法破坏既有插件。
3. **弃用策略文档化**：公开 API 变更至少经过一个版本的“标记弃用”，并在 `Plugin` 包 javadoc 页公布 changelog 锚点。
4. 插件 `class` 版本校验工具（见 R9）与宿主 JRE 检查一起做。

**成本/兼容性**：读 Manifest 为纯增量；接口若加方法务必用 `default`。建议 P0-4 与 P0-1 的“公开 API 面”配套设计。

### P1-5 扩展 `ModeHandler` 契约（生命周期 + 结果语义），保持字符串渲染兼容

**证据**
- `ModeHandler` 只有 `getModeId/getDisplayName/canPick/nextCandidate(Supplier<String>)/handleButton1Click/2Click/getButton1Text/2Text`（`ModeHandler.java:31-57`）。
- 插件模式实例是**提交期单例**（`PluginManager` 存 Handler 实例，`NamePickerApp.java:280` 直接复用），没有“被选中/被取消/卸载通知到模式”的生命周期回调。
- 候选被限定为**字符串**：主窗写 `displayLabel`（`NamePickerApp.java:466`），悬浮球有另一套截断/格式化口径（`FloatingBall.java:317-328`：>5 字截断、座位去空格），插件模式不能自定义滚动呈现。
- 抽取节奏固定（50ms / 悬浮球 20 次自停，`FloatingBall.java:240-246`），插件不可调。
- 插件模式 `schemeType` 为 null、不参与“方案类型→模式”联动（文档 §5.4/§5.5、`NamePickerApp.java:219-226`）。

**第三方影响**：玩法型插件（抽图片、抽题目带讲解、分组抽奖、轮盘式 UI）做不了“滚停引擎原生呈现”，只能结果弹窗或自绘旁路（成本高、非官方）；模式状态（暂停/重置/资源）无宿主统一管理。

**宿主改动方向（分三步，逐步放开）**
1. **模式生命周期 default 钩子**（低风险）：`default void onModeSelected()/onModeDeselected()`、卸载前若宿主在 EDT 调 `onModeAboutToUnload()`；主窗/悬浮球在切换与 `shutdown` 时调用。为不破坏现插件，做成 `ModeHandler` 的 default 方法。
2. **结果对象化（配合 P0-2）**：不改 `nextCandidate` 的字符串契约，另给事件载荷提供结构化结果（值、模式、方案、触发源）。
3. **渲染扩展（远期，成本高）**：为“候选需要富呈现”提供可选的 `CandidateView` 钩子（默认 null = 字符串路径）；主窗与悬浮球各适配一次。此项与二期交付报告“不做自绘面板/多槽位”的取舍冲突（`documents/插件UI槽二期交付报告.md` §6），建议**明确为宿主作者决策项**：若产品定位是“玩法插件平台”则做，若只定位“轻扩展”则保持字符串并文档化边界。

**成本/兼容性**：1 用 default 方法零破坏；2 增量；3 需 UI 改造，放 Stage4 评估。

### P1-6 为插件提供官方“自持数据/配置”设施（替代裸 Properties + 手工路径）

**证据**
- 文档推荐插件自持配置写到 `data/<插件名>.properties`（`插件开发文档.md:461-467`），示例自己写“默认值/合并式读写/坏值回退”工具（`TimerBallConfig.java`）。
- 路径基于 `user.dir` 的 `data/`，无宿主侧目录句柄、无“卸载后清理/隔离/命名冲突”策略；插件若误写 `data/config.properties` 会污染宿主配置（红线只是文档）。
- `PluginContext.getDataManager()` 给的是宿主实例，但文档明示“插件不要自行 new DataManager”，也没有提供“插件自有目录”的受控入口。

**第三方影响**：每个第三方都要自己造配置轮子，且与宿主文件布局耦合（依赖 `user.dir`）；误操作风险高。

**宿主改动方向**
1. `PluginContext` 新增 `File getPluginDataDir()`（宿主按插件名在 `data/plugins/<pluginKey>/` 下创建并返回），`java.util.Properties` 用法不变但路径受控。
2. 新增一个薄封装 `PluginConfig`（默认值 + 合并读写 + 类型解析 + 写失败仅日志），把 `TimerBallConfig` 的成熟做法收编为官方小工具，减少重复实现。
3. 文档明确：卸载/删除 jar **不自动删除**插件数据（保护用户数据），但宿主可提供“插件数据占用查看”（配合 P0-3 状态页）。

**成本/兼容性**：增量；保留旧约定（仍允许插件自管文件）即可。

### P1-7 提升 UI 动作的表达力与诊断性（图标/提示/顺序/分组/动态显隐，可选不破坏）

**证据**
- `addUiAction(UiZone, String title, ActionListener)` 是唯一入口（`PluginContext.java:43`）；空 title/action **静默忽略**（`PluginManager.java:174-176`），第三方点了“没反应”也查不到原因（文档第 11 章 FAQ 已有此条，但只让看日志）。
- 主窗按钮区固定“两列向下”、每动作一个按钮（`NamePickerApp.java:348-371`），菜单区只能平铺项（`Main.java:121-128`、`FloatingBall.java:149-161`）；二期交付报告明确不做“多槽位/分组/图标/排序”（`documents/插件UI槽二期交付报告.md` §6）。

**第三方影响**：动作多时 UI 扁平无结构；无法表达“此按钮在无抽取结果时应禁用/隐藏”；无图标/提示。
（对课堂工具属低优先，但对“插件市场式”增长会是体验硬伤。）

**宿主改动方向**
1. **不破坏现 API 的扩展**：新增可选 `PluginContext.addUiAction(UiZone zone, ActionSpec spec)`（`ActionSpec` 含 title、`ActionListener`、可选 tooltip/iconKey/order/group/`Supplier<Boolean> enabled`）；现有 `addUiAction(title,action)` 委托为默认 spec，渲染端只读 `ActionSpec`。
2. **静默忽略改显式**：空 title/action 至少记一条带插件名的 `PLUGIN_LOAD_ERROR`（或返回 boolean），避免“注册了但没出现且无日志”。
3. 状态页（P0-3）顺带展示每个插件注册的动作清单与 Zone 分布，帮助第三方核对。

**成本/兼容性**：全增量；注意各渲染端（主窗/托盘/悬浮球/五对话框）同步读 spec 字段即可。

### P1-8 开发循环与自动化：最小热重载/禁用、TestHost、headless 加载验证

**证据**
- 增删插件/改注册都必须重启（文档 §3.5、`PluginManager` 无重扫路径）；二期交付报告“明确不做”热插拔。
- `PluginManager` 是单例且必须 `init(ModeHost)`（`PluginManager.java:227-229`），ModeHost 的唯一实现是 `NamePickerApp`（主窗）；测试只能走 UI 自动化或用 `loadAllSync()`（`PluginManager.java:252-257`，仍需真宿主）。
- 示例插件的“验证”是人工重启 + 看日志（`插件开发文档.md:291-296`）。

**第三方影响**：开发一次改动 = 一次完整重启；无人值守 CI 只能驱动真实 UI；单测无从写起。

**宿主改动方向**
1. **零成本小步**：扫描时跳过 `*.jar.disabled`（或支持 `plugins_disabled.txt`），让第三方/用户“禁用一个 jar”不必物理删除——不改加载内核。
2. **TestHost/Stub 随仓库或文档提供**：一个实现 `ModeHost` 的内存桩（假 Scheme/NameManager/DataManager）与 `PluginContext` 的轻量实现（或把 `PerPluginContext` 提为可构造的公开测试形态），配合 `loadAllSync()` 做“无 UI 加载→断言注册结果/冲突拒载”的 JUnit 式验证。
3. **headless 自检开关**（可选）：宿主加一个命令行开关（如 `--plugin-check`），启动后同步加载插件、把每个 jar 的 outcome 打到 stdout/日志并以退出码反映成败，供 CI 用。
4. **开发期热重载**：明确属于 Stage4（与“运行中热插拔”同轨道），不建议在 1.x 抢先做全量热插拔；可先做“手动触发重载”（菜单项/键位），复用现有暂存-提交管线把整套 UI 刷新跑一遍。

**成本/兼容性**：1、2 低；3、4 中。建议 1+2 先落地（对第三方开发体验提升最大）。

### P1-9 第三方构建工具链：模板工程 + 一键校验脚本

**证据**
- 文档给了 javac/jar 命令（`插件开发文档.md:254-279`），但没有可直接复制改名的“模板工程”，也没有“自检脚本”校验打包禁令/class 版本。
- 打包禁令“jar 内不出现 `com/randomnamepicker/`”靠 `jar tf` 手工自查（`插件开发文档.md:277-279`）。

**第三方影响**：每个第三方都要重读 BUILD 说明；最常犯的“把宿主/API 类打进 jar”“class 版本过高”无工具化拦截，拒载后还得自己翻日志。

**宿主改动方向（仓库内示例/工具即可，非宿主运行时）**
1. 新增 `examples/plugin-template/`（源码骨架 + `BUILD.bat` + 说明），与 `plugin-example` 对齐但留 TODO 注释。
2. 提供 `tools/check_plugin.bat`（或文档化一条 `jar tf`+`javap` 组合命令）：检查 jar 内无 `com/randomnamepicker/` 条目、class 主版本 ≤ 目标 JRE（对目录逐一读 class 文件头 6-8 字节判断 major version）。
3. 编译指引建议加 `javac --release`（或明确 `-source/-target`）与“目标 JRE 检查”步骤（文档修订 D2）。

**成本**：低；纯示例与脚本，不影响宿主行为。

### P1-10 加载顺序与显示秩序显性化

**证据**
- 加载顺序 = **plugins/ 目录按文件名排序**（`PluginManager.java:316`）；同序冲突“先到先得”，后到者整 jar 拒载（`PluginManager.java:449-454`）。
- 菜单/下拉框顺序 = 提交序；插件无法表达“我想排在另一插件前/后”或分组。
- 一个 jar 可含多个 `Plugin` 候选（共享 loader、独立 context，`PluginManager.java:354-373`），但外部无“按 jar 分组展示/管理”视图。

**第三方影响**：当第三方插件多了，谁先谁后靠文件名碰运气；冲突时只见“与已加载插件冲突”，没有“是谁先占”。

**宿主改动方向**
1. 加载结果状态（P0-3）里记录冲突双方名称；拒载原因给出“已被 X 占用”。
2. 可选 `PLUGIN_ORDER` 清单（`plugins/order.txt` 或 Manifest 优先级属性）显式排序；默认仍按文件名，保持现状兼容。
3. 主窗/托盘动作区支持“按插件分组（子菜单/分隔）”（与 P1-7 的 group 合并设计）。

**成本/兼容性**：1 低；2、3 中。第三方刚起步时 1 就够。

### P2-11 信任/安全模型：如实文档化 + 可选“未知插件首启确认”

**证据**
- 无签名/校验/沙箱（交付报告明示“签名/权限校验”不做，`documents/Stage3_交付报告.md:80`）；JVM 进程内，插件可读全部解密名单、可经 `PasswordManager.unlock()` 解锁（见 P0-1 证据）。
- 现有文档措辞（“插件 API 不暴露密码/锁相关类”，`插件开发文档.md:42`）在字面上**低估了可达性**，会给第三方与终端用户错误的安全预期。

**第三方影响/风险**：若按“插件 = 可执行代码”的常识，当前等于**完全信任模型**。对课堂自用无碍；对第三方分发，安装方应有知情。

**宿主改动方向**
1. 文档显式声明信任模型：“插件与本程序同权限，可访问本机数据；请仅安装可信来源插件”，并给出“运行目录”与 `data/` 的含义（D1）。
2. （可选）首次加载非宿主自带插件时弹一次确认/提示（可记住）；对 jar 无签名只提示不拦截——避免给用户虚假安全感，也避免误伤。
3. 明确不承诺：沙箱、撤销、按插件隔离数据。（不建议实现，理由见 §7。）

**成本**：1 零代码；2 是 SettingsWindow/PluginManager 小改。

### P2-12 主题/窗口引擎与插件窗口的互操作显性化

**证据**
- 宿主背景主题按**宿主窗口类名白名单**自动装配，插件自有窗口默认豁免（`BackdropManager.java:59-60, 100-120` `categoryOf` 未列即豁免）；悬浮球/计时子球也在豁免列表讨论过（`documents/背景主题插件开发方案.md:26`）。
- 文档与示例均未向第三方说明“你的窗口会不会被主题影响、如何自选是否参与”。

**第三方影响**：第三方自绘窗口（如正计时子球）与主题互不干扰，但这属于“碰巧豁免”而非“契约”；将来主题扩白名单时可能误伤，插件作者无法表达意愿。

**宿主改动方向**
1. 文档在插件开发章节补一节“宿主主题（背景图）与插件窗口关系：默认豁免、白名单在 `BackdropManager`、插件不得依赖主题行为”。
2. （可选）`PluginContext` 提供只读 `boolean isThemeFeatureAvailable()` 之类，供插件判断是否要避开主题占位，优先级低。

**成本**：低。

### P2-13 命名与标识卫生：modeId 优先、displayName 仅展示

**证据**
- 插件模式对外键实际是 **displayName 字符串**：`getPluginModeHandler(displayName)`（`PluginManager.java:549-558`）、模式下拉框项就是 displayName（`NamePickerApp.java:398-421`）、日志“方案-模式显示名=结果”（`NamePickerApp.java:514-521`）；悬浮球右键也按显示名 switch（`FloatingBall.java:120-141`）。
- displayName 用于 UI 展示与标识双重身份：改文案会改变所有引用语义；不同语言/重名风险文档只靠“判重”兜底。

**第三方影响**：第三方若想“展示名本地化/品牌化”会与“模式标识”纠缠；宿主 API 用显示名做键是隐式耦合。

**宿主改动方向**
1. 事件/查询新 API 一律用 `modeId` 传参，displayName 仅展示（旧 API 保留兼容）。
2. 冲突预检与日志同时带上 modeId 与 displayName，方便排查。

**成本**：配合 P0-2/P0-3 增量做，无独立成本。

## 6. “如果只做三件事”的最小必要改动集

若宿主作者想以最小成本显著改善第三方体验，按性价比排序：

1. **加载结果可观测**（P0-3 简化版）：`PluginManager` 记录每 jar 成败与原因，设置窗/插件菜单增加一个只读“插件状态”入口。——第三方“装完看得到为什么没生效”，直接消除最大反馈黑洞。
2. **抽取结果/宿主状态事件**（P0-2 简化版）：在 `logResult()` 等收敛点发出结构化事件，`PluginContext` 提供订阅/退订并在 onUnload/回滚时自动清理。——第三方最想要的“结果与状态联动”能力，且消灭绕路写法。
3. **文档信任模型 + 打包自检**（D1 + R9 简化版）：如实声明“完全信任、内部类可达、仅受文档约束”，并给出 jar 自检命令。——立刻消除文档与事实的矛盾，防第三方踩坑。

这三项都不触碰加载内核、不破坏现有插件二进制，可与 1.x 并行。

---

## 7. 不建议做的宿主改动（及理由）

1. **JPMS 模块化（module-info）收紧 API 面**：宿主当前是 classpath 启动、无模块化，引入 JPMS 需 jlink/模块化打包整体改造（含既有 jar 启动方式），与 Stage4 的 jlink 规划有重叠但成本高、回归面大；不如 P0-1 的“白名单 + 加载期自检 + 文档”组合务实。
2. **SecurityManager/沙箱**：现代 JDK 已弃用/移除 SecurityManager 路线，无法低成本获得真实隔离；应维持“完全信任 + 文档 + 用户确认”（P2-11）。
3. **在 1.x 抢做全量运行中热插拔**：暂存-提交管线虽便于复用，但涉及“卸载后 UI 项移除、加载器生命周期、运行中模式切换一致性”等多个未决面；先做“手动重载/禁用 jar”（P1-8.1/8.4）更稳。
4. **插件间依赖解析/插件市场/签名体系**：交付报告已列“不做”，对当前规模属过度设计；若真到“插件平台”阶段再单独立项。
